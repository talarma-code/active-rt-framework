= ActiveRT Core
:toc:
:toclevels: 2
:sectnums:

Lightweight C++ utilities for *ESP32 FreeRTOS* applications.

ActiveRT provides deterministic, ISR-safe abstractions for tasks,
queues and memory pools, designed specifically for real-time embedded systems.
It is **FreeRTOS-specific** and intentionally minimal.

== Architecture Overview

ActiveRT is a small runtime layer built on top of *FreeRTOS*.
It does not replace FreeRTOS primitives, but wraps them in explicit,
type-safe C++ abstractions.

=== Design Goals

* Deterministic execution
* No dynamic allocation during runtime
 └─ loop()    // called repeatedly
----

=== Characteristics


=== Watchdog Usage Example

This example shows how to enable the Task Watchdog for an `ActiveTask`-based
worker task and feed it from `loop()`:

[source,cpp]
----
class CommsTask : public ActiveTask {
public:
    CommsTask()
        : ActiveTask("comms", 4096, 3) {}

    void setup() override {
        // initialization
    }

    void loop() override {
        // communication logic

        // feed task watchdog for this ActiveTask instance
        resetWatchdog();

        vTaskDelay(pdMS_TO_TICKS(50));
    }
};

CommsTask commsTask;

void initTasks() {
    // Initialize global Task WDT once (shared timeout for all ActiveTask instances)
    ActiveTask::initWatchdog(10); // seconds

    // Enable watchdog monitoring for this specific task
    commsTask.enableWatchdog(true);

    // Start the FreeRTOS task
    commsTask.start();
}
----
* FreeRTOS-specific
* Cooperative by default (explicit delay or yield)
* No implicit blocking
* Clear ownership of task resources

=== Task Watchdog Integration (ESP32 Task WDT)

`ActiveTask` optionally integrates with the ESP32 *Task Watchdog* (`esp_task_wdt`).

Key APIs:

* `static void initWatchdog(uint32_t timeoutSeconds)`
** Initializes the global Task WDT with a *shared timeout* for all registered tasks
** Must be called once from `setup()` / main initialization code
* `void enableWatchdog(bool enable = true)`
** Enables or disables watchdog monitoring for a given `ActiveTask` instance
** Must be called *before* `start()` to register the FreeRTOS task in the watchdog
* `void resetWatchdog()`
** Feeds the Task WDT for this task
** Should be called from `loop()` often enough to stay within `timeoutSeconds`

Notes:

* All tasks share the same timeout configured via `initWatchdog()`
* Internally `ActiveTask` uses `esp_task_wdt_add(nullptr)` in the task entry point
* Tasks that may legally block for long periods *should not* enable the Task WDT

=== Example

[source,cpp]
----
class WorkerTask : public ActiveTask {
public:
    WorkerTask()
        : ActiveTask("worker", 4096, 2) {}

    void setup() override {
----

=== Watchdog Usage Example

Typical pattern on ESP32 with Arduino:

[source,cpp]
----
WorkerTask commsTask;
WorkerTask loggerTask;

void setup() {
    // 1) Initialize global Task WDT (shared timeout)
    ActiveTask::initWatchdog(10); // seconds

    // 2) Optionally monitor the Arduino loop task as well
    esp_task_wdt_add(nullptr);

    // 3) Enable watchdog for selected ActiveTask instances
    commsTask.enableWatchdog(true);
    loggerTask.enableWatchdog(true);

    commsTask.start();
    loggerTask.start();
}

void loop() {
    // Application logic
    // ...

    // Feed watchdog for Arduino loop task
    esp_task_wdt_reset();
}
    }

    void loop() override {
        // task logic
        vTaskDelay(pdMS_TO_TICKS(10));
    }
};
----

== ActiveQueue and ActiveQueueRef

=== ActiveQueue<T>

`ActiveQueue<T>` is an owning, type-safe wrapper around a FreeRTOS queue.

It is used for communication between tasks and from ISR to task.

==== OS Mechanism

* Wraps `QueueHandle_t`
* Uses `xQueueCreate`, `xQueueSend`, `xQueueReceive`
* Supports ISR-safe variants

==== Characteristics

* Owns the underlying FreeRTOS queue
* Copies elements of type `T`
* Thread-safe and ISR-safe
* No allocation after construction

==== Timeout Semantics

All `send` / `receive` timeouts are expressed in **milliseconds**.

Each `ActiveQueue<T>` exposes two constants:

* `ActiveQueue<T>::kDefaultTimeoutMs`
** Default timeout used when no explicit value is provided
** In the current implementation: `500` ms
* `ActiveQueue<T>::kWaitForeverMs`
** Sentinel value mapped to `portMAX_DELAY` in FreeRTOS ticks
** Use this when you intentionally want to block forever

==== Example

[source,cpp]
----
struct Message {
    int value;
};

ActiveQueue<Message> queue(10);

Message msg{42};
queue.send(msg); // uses kDefaultTimeoutMs (non-infinite wait)

Message rx;
queue.receive(rx, ActiveQueue<Message>::kWaitForeverMs);
----

==== ISR Usage

[source,cpp]
----
BaseType_t hpw = pdFALSE;
queue.sendFromISR(msg, &hpw);

if (hpw) {
    portYIELD_FROM_ISR();
}
----

=== ActiveQueueRef<T>

`ActiveQueueRef<T>` is a *non-owning reference* to an existing FreeRTOS queue.

It allows passing queue access into tasks without transferring ownership.

==== Characteristics

* Lightweight wrapper (stores only `QueueHandle_t`)
* Same API as `ActiveQueue<T>`
* Does not create or delete the queue

`ActiveQueueRef<T>` also exposes the same timeout constants:

* `ActiveQueueRef<T>::kDefaultTimeoutMs`
* `ActiveQueueRef<T>::kWaitForeverMs`

==== Example

[source,cpp]
----
ActiveQueue<Message> queue(10);
ActiveQueueRef<Message> ref(queue.nativeHandle());
----

== ActivePool and ActivePoolRef

=== Motivation

Dynamic memory allocation is unsafe in ISR context and undesirable
in real-time systems due to fragmentation and nondeterministic timing.

`ActivePool<T>` provides a deterministic alternative.

=== ActivePool<T>

`ActivePool<T>` is a fixed-size, ISR-safe object pool implemented
using a FreeRTOS queue of pointers.

==== OS Mechanism

[source]
----
static T objects[N];
Queue<T*> freeList;
----

* Objects are preallocated
* Queue stores pointers to free objects
* `acquire()` removes a pointer from the queue
* `release()` returns it back

==== Characteristics

* FreeRTOS-specific
* No dynamic allocation after construction
* Constant-time operations (O(1))
* Explicit ownership transfer
* ISR-safe acquire and release

==== Typical Pattern

[source]
----
ISR
 ├─ acquireFromISR()
 ├─ fill object
 └─ enqueue pointer

Task
 ├─ receive pointer
 ├─ process object
 └─ release()
----

==== Example (ESP-NOW style)

[source,cpp]
----
ActivePool<Packet> pool(8);
ActiveQueue<Packet*> workQueue(8);

void onReceiveISR(...) {
    BaseType_t hpw = pdFALSE;

    Packet* pkt = pool.acquireFromISR(&hpw);
    if (!pkt) {
        return; // drop packet
    }

    workQueue.sendFromISR(pkt, &hpw);

    if (hpw) {
        portYIELD_FROM_ISR();
    }
}
----

=== ActivePoolRef<T>

`ActivePoolRef<T>` is a non-owning reference to an existing `ActivePool`.

It allows tasks to use the pool without owning or managing its lifetime.

==== Characteristics

* Lightweight wrapper
* ISR-safe
* Same acquire/release API as `ActivePool<T>`
* Does not manage memory or lifetime

==== Example

[source,cpp]
----
ActivePool<Packet> pool(8);
ActivePoolRef<Packet> poolRef(pool.nativeHandle());
----

== SystemTimer (FreeRTOS Software Timer Wrapper)

`SystemTimer` is a lightweight C++ wrapper around **FreeRTOS software timers**
(`xTimerCreate`) designed for **event-driven systems** on ESP32.

It integrates directly with the Active RT Framework by sending timer events
to an `ActiveQueue` via `ActiveQueueRef`, allowing all timing logic to be
handled inside normal tasks instead of timer callbacks.

This design avoids polling, blocking delays, and complex timing logic
inside application tasks.

---

=== Design Goals

* Fully event-driven (no `vTaskDelay()` in application code)
* Safe to use with FreeRTOS Timer Service Task
* Zero dynamic allocation after system startup
* Minimal timer callback logic
* Seamless integration with `ActiveQueue`
* Suitable for ISR-safe and RTOS-safe designs

---

=== How It Works

* `SystemTimer` wraps a FreeRTOS software timer
* When the timer expires, the callback:
  - creates a `TimerEvent`
  - sends it to an `ActiveQueue` using `sendFromISR()`
* The application task receives and processes the event

IMPORTANT:  
The timer callback executes in the context of the **FreeRTOS Timer Service Task (`Tmr Svc`)**.
It must never block, allocate memory, or perform heavy logic.

---

=== Timer Event Type

Timers generate a small, deterministic event structure:

[source,cpp]
----
enum class TimerEventType : uint8_t {
    Fired
};

struct TimerEvent {
    uint32_t timerId;
    TimerEventType type;
};
----

* `timerId` is user-defined and allows one task to handle multiple timers
* `type` enables future extensions (e.g. Stop, Restart)

---

=== Class Overview

[source,cpp]
----
class SystemTimer {
public:
    enum class Mode {
        OneShot,
        Periodic
    };

    SystemTimer(
        uint32_t timerId,
        uint32_t periodMs,
        Mode mode,
        ActiveQueueRef<TimerEvent> eventQueue
    );

    bool start();
    bool stop();
    bool reset();
};
----

---

=== Constructor Parameters

|===
| Parameter | Description

| `timerId`
| Application-defined identifier delivered with each timer event

| `periodMs`
| Timer period in milliseconds

| `mode`
| `OneShot` or `Periodic`

| `eventQueue`
| Reference to an existing `ActiveQueue` used to deliver events
|===

---

=== One-Shot Timer Example

[source,cpp]
----
ActiveQueue<TimerEvent> timerQueue(4);
ActiveQueueRef<TimerEvent> timerQueueRef(timerQueue);

SystemTimer retryTimer(
    1,

retryTimer.start();
----

=== Periodic Timer Example

[source,cpp]
----

    SystemTimer::Mode::Periodic,

heartbeatTimer.start();
----

=== SystemTimerT (templated variant)

`SystemTimerT` is a header-only templated variant of `SystemTimer` that does not require
the framework to know about application-specific message types. Instead of sending
`TimerEvent` directly, it converts a `TimerEvent` into a user-defined `MessageT` via
a lightweight, ISR-safe converter functor and delivers `MessageT` to an
`ActiveQueue<MessageT>` via `ActiveQueueRef<MessageT>`.

==== Key points

* `MessageT` is the type placed on the queue (e.g. `TimerEvent` or a small app-defined struct)
* `Converter` is a callable: `MessageT operator()(const TimerEvent&)`
* Converter must be **ISR-safe** (no dynamic allocation, no blocking calls)
* Default converter `DefaultTimerToMessageConverter<MessageT>` constructs `MessageT` from `TimerEvent`

IMPORTANT: Keep converter logic minimal — the conversion runs in the timer callback
context (FreeRTOS Timer Service Task) and must not allocate or block.

----

==== Example 1 — Default converter (`MessageT == TimerEvent`)

This is the simplest case — use the default converter and a queue of `TimerEvent`.

[source,cpp]
----
ActiveQueue<TimerEvent> timerQueue(4);
ActiveQueueRef<TimerEvent> timerQueueRef(timerQueue);

// Default converter returns TimerEvent directly, so no extra setup is needed
SystemTimerT<TimerEvent> tmr(
    1,
    1000,
    SystemTimerT<TimerEvent>::Mode::Periodic,
    timerQueueRef
);

tmr.start();
----

==== Example 2 — Custom converter (application message)

If the application queue uses a custom message type, provide a small converter
that maps `TimerEvent` to your `MessageT`.

[source,cpp]
----
struct MyMsg {
    uint32_t srcTimerId;
    uint32_t extra;
};

struct TimerToMyMsg {
    MyMsg operator()(const TimerEvent& t) const noexcept {
        MyMsg m{};
        m.srcTimerId = t.timerId;
        m.extra = 0; // fill with application data if required
        return m;
    }
};

ActiveQueue<MyMsg> myQueue(4);
ActiveQueueRef<MyMsg> myQueueRef(myQueue);

SystemTimerT<MyMsg, TimerToMyMsg> myTimer(
    2,
    500,
    SystemTimerT<MyMsg, TimerToMyMsg>::Mode::OneShot,
    myQueueRef,
    TimerToMyMsg()
);

myTimer.start();
----

---

=== Receiving Timer Events in a Task

[source,cpp]
----
void loop() override {
    TimerEvent evt;

    if (timerQueue.receive(evt, ActiveQueue<TimerEvent>::kWaitForeverMs)) {
        switch (evt.timerId) {
            case 1:
                // retry timeout
                break;

            case 2:
                // heartbeat
                break;
        }
    }
}
----

This approach allows the task to sleep until an event occurs,
resulting in low CPU usage and deterministic timing behavior.

---

=== RTOS Safety Rules

The following rules are strictly enforced by the design:

* Timer callbacks never block
* Timer callbacks never allocate memory
* Timer callbacks never access Serial or logging APIs
* All application logic runs in normal task context

This makes `SystemTimer` safe to use alongside:
* ESP-NOW
* WiFi stack
* Other ESP-IDF and Arduino background tasks

---

=== Why Use SystemTimer Instead of vTaskDelay()

| `vTaskDelay()` | `SystemTimer` |
|---------------|---------------|
| Polling-based | Event-driven |
| Task blocked | Task sleeps until event |
| Hard to scale | Easy to manage multiple timers |
| Logic mixed with timing | Clear separation |

---

=== Typical Use Cases

* Retries and backoff timers
* Heartbeat / watchdog events
* Deferred execution
* Timeouts for communication protocols
* Periodic status updates

---

=== Summary

`SystemTimer` provides a clean, deterministic, and scalable way to handle
time-based events in FreeRTOS-based systems.

By combining software timers with `ActiveQueue`, it enables a pure
event-driven architecture suitable for professional embedded applications
on ESP32.


== Default ESP32 / Arduino Tasks (FreeRTOS)

When using *ESP32 with Arduino framework* (including PlatformIO),
the system runs **much more than just your application task**.

Arduino on ESP32 is built on top of *ESP-IDF*, which itself uses *FreeRTOS*.
As a result, the runtime environment consists of multiple system, network,
and service tasks that are created automatically at startup.

This section explains the most common default tasks you will see when
calling `vTaskList()` or similar diagnostic APIs.

---

=== Example Task List

Below is an example output from `vTaskList()` on ESP32 with Arduino enabled:

[source,text]
----

---------------------------------------------

IDLE0           R       0      504    5    0
IDLE1           R       0      580    6    1
tiT             B      18     3640   10    0
ipc1            S      24      488    2    1
sys_evt         B      20     3444   11    0

Tmr Svc         B       1     3600    7    -
----

This is a *normal* and *expected* configuration.

---

=== Application-Level Tasks

==== loopTask
* Created by Arduino framework
* Executes `setup()` once, then repeatedly calls `loop()`
* Priority: 1
* Usually pinned to Core 1
* This is the main application task for Arduino users

---

=== FreeRTOS System Tasks

==== IDLE0 / IDLE1
* Idle tasks (one per CPU core)
* Executed when no other task is ready to run
* Responsible for:
  - task cleanup
  - idle hooks
* Priority: 0

==== Tmr Svc (Timer Service Task)
* Handles FreeRTOS software timers (`xTimerCreate`)
* Executes timer callbacks
* Priority: 1
* Required for any FreeRTOS timer usage

---

=== ESP-IDF Core System Tasks

==== esp_timer
* High-resolution timer service
* Used internally by:
  - WiFi
  - ESP-NOW
  - Arduino timing functions (`millis()`, `delay()`)
* Priority: 22
* Large stack by design
* **Must never be blocked**

==== sys_evt
* ESP-IDF system event loop
* Processes system-level events:
  - WiFi connect / disconnect
  - IP acquisition
* Priority: 20

==== ipc0 / ipc1
* Inter-Processor Communication tasks
* Used for synchronization between CPU cores
* Very high priority (24)
* Internal system mechanism — do not interact directly

==== tiT
* Timer interrupt handling task
* Part of ESP-IDF internal timing subsystem
* High priority
* Not user-accessible

---

=== Arduino / Networking Tasks

==== wifi
* WiFi and networking stack
* Used by:
  - WiFi
  - ESP-NOW
  - TCP/IP
* Priority: 23
* Critical for radio and network operation
* **User code must never block this task**

==== arduino_events
* Arduino event dispatcher task
* Handles:
  - `WiFi.onEvent()`
  - Arduino-level callbacks
* Priority: 19

---

=== Practical Notes for Active RT Framework Users

* The number of default tasks is higher than on bare FreeRTOS systems
* This is expected and does not indicate misconfiguration
* Users should:
  - Avoid blocking system tasks
  - Use moderate priorities for custom tasks (typically 2–5)
  - Monitor stack usage and free heap
* `ActiveTask` instances should be pinned and prioritized consciously
* ISR handlers (e.g. ESP-NOW receive callbacks) should remain minimal
  and delegate work via `ActiveQueue`

---

=== Summary

* ESP32 + Arduino runs a full RTOS-based system
* Multiple system and service tasks are always present
* Most tasks are internal and should not be modified
* Application logic should coexist with, not fight against, the runtime

Understanding these default tasks helps design safe, efficient,
and predictable real-time systems using the Active RT Framework.


== StaticString

`StaticString<N>` is a fixed-capacity, real-time safe string class.

It stores text in an internal buffer of compile-time defined size
and never performs dynamic memory allocation.

=== Characteristics

* FreeRTOS-friendly
* No heap usage
* Deterministic execution
* Copyable and queue-safe
* Truncates on overflow (no exceptions)

=== Example

[source,cpp]
----
StaticString<32> name("esp32");
name.append("-node");
----


== Important Rules and Best Practices

WARNING: Objects that use FreeRTOS primitives (`Queue`, `Task`, `Semaphore`)
must be constructed *after* the FreeRTOS scheduler is initialized.

WARNING: Avoid static initialization and classic singleton patterns.

TIP: Prefer explicit ownership and dependency injection.

TIP: Use finite queue timeouts by default (e.g. `kDefaultTimeoutMs = 500`) and
only use `kWaitForeverMs` when a true infinite wait is intentional and safe
for the given task.

== Design Philosophy

[quote]
____
Deterministic behavior is more important than convenience.
Explicit ownership is better than hidden global access.
____
